## src/lib rules
- Account creation, deactivation and password resets go through server functions in `src/lib/equipe.functions.ts` (service-role, master-checked). Public signup is disabled; each clinic's first master is created by the developer panel (`criarClinica`). Team functions only touch accounts of the caller's clinic.
- Data reads use `queryOptions` in `src/lib/queries.ts` with the browser client (RLS applies), loaded via route loaders + `useSuspenseQuery`.
- Business rules have tests next to them (`regras.test.ts`, `indicadores.test.ts`, etc.); add one per new rule.
- Financial exports (PDF/CSV/XLSX) are generated in the browser by `exportar-financeiro.ts` from the rows already loaded on the Financeiro page, with jspdf/exceljs imported lazily on click. Why: exports respect the same RLS-filtered data the user sees and keep heavy libs out of the initial bundle.
- Patient charges (Asaas): each clinic pastes its OWN API key on the Financeiro page, Cobranças tab (old `/$clinica/cobrancas` URL redirects there) (`recebimentos.functions.ts`, gestor only); the key is validated, stored AES-GCM encrypted (`PAGAMENTOS_CHAVE_CRIPTO`) in `pagamento_contas` (service-role only, no RLS policies), and a per-clinic webhook with its own token is registered. The developer panel only reads the status. Charges live in `cobrancas`/`cobranca_itens`, created by `cobrancas.functions.ts`; parents pay on the public `/pagar/$token` page (`pagamento-publico.functions.ts`, card data forwarded to Asaas, never stored/logged). Webhooks hit `/api/public/asaas/webhook`, verified by the clinic's `asaas-access-token` hash; `aplicarSituacao` in `pagamentos.server.ts` is the single place that syncs status and marks linked sessions paid. Why: each clinic's money and credentials are its own, parents only see CliniHelp, keys never reach the browser.
- Indicators (`$clinica/indicadores`, gestor + financeiro only) are computed in the browser from RLS-filtered sessions by pure functions in `indicadores.ts`; opening hours for room occupancy are a per-browser localStorage preference. Why: no new money-exposing endpoint, and the formulas stay testable.
- Waiting list lives in `lista_espera` (all staff read; gestor/recepção write), with queue order/position rules in `lista-espera.ts`; scheduling from it reuses `AgendamentoDialog` and marks the request "agendado". Why: one scheduling flow keeps the double-booking protections.
- Therapy plan: goals in `plano_metas` and per-session levels (1–5) in `evolucao_metas`, both gated like `evolucoes` (`can_view_especialidade` to read, specialty members write; progress only by the evolution's author); administrador cannot see them in the audit log. Chart/summary/report math lives in `plano-terapeutico.ts`. Why: goals and progress are clinical record data.
- Evolution templates live in `modelos_evolucao` (staff read, specialty members or gestor write); a built-in default shows when a specialty has none.
- Voice dictation: browser records 16 kHz WAV (`gravar-voz.ts`) and POSTs to `/api/evolucao-voz`, which checks the bearer + `has_especialidade`, transcribes and then rewrites with the AI gateway (`evolucao-voz.server.ts`); it never saves — the text goes back into the form for the professional to review. Why: AI output must be human-reviewed before it becomes a legal record.
- Patient PDF report (`relatorio-paciente.ts`) is built in the browser from RLS-filtered evolutions/goals, jspdf loaded on click. Why: same reason as financial exports.
- Family area (`/familia`, public route with inline code login, `ssr: false`): parents get passwordless accounts created only by `enviarCodigoFamilia` after their e-mail is found on an active patient (any of the 3 responsável e-mails). All family reads go through SECURITY DEFINER `familia_*` RPCs gated by `responsavel_de`/`familia_sessao_ok` (account with no clinic profile, no roles, not a developer); parents get no RLS access to business tables. Why: staff e-mails are chosen by the clinic, so staff accounts must never unlock family data, and RPCs expose only parent-safe columns.
- Signed terms live in `termos_assinaturas`: text is snapshotted and hashed by DB trigger at request, staff can only cancel pending rows, and signing is written by `assinarTermo` (service role, after the parent's RPC check) with IP/device/hash. Released reports are PDFs in the private `relatorios-familia` bucket + `relatorios_liberados`, downloaded by parents via short-lived signed URLs from `baixarRelatorioFamilia`.
- Insurance guides: `guias_convenio` (3 required codes, requested/authorized counts, dates, attachment in private `guias-convenio` bucket), per-session `liberacoes_atendimento` (daily release status/token/guide link) and `glosas`, only for plans of type `convenio` (`exigeGuia`; liminar works like particular); balance comes from the `guias_uso` view (finalized sessions linked to the guide = used). The `vincular_guia_sessao` trigger auto-links a valid guide when a session reaches aguardando/em_atendimento/finalizado; alert/balance/renewal/glosa math lives in `guias.ts`. Glosa values and session prices are gestor/financeiro only. Why: the balance must be computed in one place so it never double-counts, and reception keeps no access to money.
- Liminar closing (`$clinica/liminares`, gestor + financeiro only): one `faturas_liminar` row per patient/month (NF number + issue date; `vencimento` is a generated column = issue + 30 days, mirrored by `DIAS_PAGAMENTO_LIMINAR` in `liminar.ts`) and `fatura_liminar_itens` (one finalized session belongs to one closing, same patient/month enforced in `garantir_mesma_clinica`). Totals are recalculated by statement-level triggers; setting status `paga` marks the linked sessions paid (and undoing reverts). Attendance-list PDF is built in the browser by `lista-presenca.ts`. Why: the 30-day rule and totals live in the database so the KPI and the page never disagree.
- Appointment status machine (`agenda-status.ts`): agendado → aguardando → em_atendimento → finalizado, plus falta_justificada / falta_terapeuta / falta_cobrada / cancelado. DB triggers own the side effects: `agendamento_status_carimbo` stamps times, `sincronizar_financeiro_status` sets `atendimento_financeiro.cobrar/repassar` (mirrored by `regraFinanceira`), `finalizar_sessao_pela_evolucao` finalizes on a linked evolution. Money totals use `valorCobrado`/`repasseDevido` from `financeiro.ts`, never raw `valor`/`valor_repasse`. Absence certificates are `paciente_documentos` rows with `agendamento_id`, in the `documentos-pacientes` bucket. Why: reception changes status without touching money tables, and every report applies the same charge/payout rule.
